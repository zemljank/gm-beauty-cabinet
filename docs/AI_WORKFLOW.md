# Совместная работа Cursor, Codex и GitHub

Cursor и Codex не должны одновременно править одну рабочую папку. Общая точка
координации — GitHub: отдельная ветка и worktree для реализации, Pull Request для
обсуждения, CI для объективной проверки, второй инструмент для код-ревью.

## Роли

- **Исполнитель:** либо Cursor, либо Codex. Он один меняет код задачи.
- **Ревьюер:** второй инструмент читает diff или PR и ищет ошибки, но не пишет в
  ветку исполнителя.
- **Владелец:** человек принимает продуктовые решения и разрешает merge/deploy.

Для следующей задачи роли можно поменять. Так оба инструмента помогают проекту,
но не перетирают работу друг друга.

## 1. Начало задачи

В основной копии репозитория сначала только проверьте состояние:

```bash
git status --short --branch
git fetch --prune origin
```

Если есть незакоммиченные изменения или stash, не переносите и не удаляйте их.
Создайте отдельный worktree от актуального `origin/main`:

```bash
# Задача для Cursor
git worktree add ../gm-beauty-cursor-<task> -b cursor/<task> origin/main

# Задача для Codex
git worktree add ../gm-beauty-codex-<task> -b codex/<task> origin/main
```

В приложении Codex можно выбрать создание нового worktree и базу `origin/main` —
это предпочтительнее ручной команды. В Cursor откройте именно созданную папку,
а не исходную рабочую копию.

Имена `<task>` должны быть короткими и понятными, например
`mobile-catalog-filters`. Не используйте одну ветку повторно для другой задачи.

## 2. Перед изменениями

В новом worktree:

```bash
npm ci
npm run lint
npm run build
```

Так фиксируется исходное состояние. Если базовая проверка уже падает, исполнитель
останавливается и сообщает ошибку отдельно — не маскирует её случайным рефакторингом.

Пример задания исполнителю:

> Прочитай AGENTS.md и релевантные файлы. Сначала проверь git status и опиши
> границы задачи. Реализуй только согласованный scope. Не коммить и не пушь без
> моего разрешения. После изменений запусти lint и build, а для интерфейса проверь
> 390 и 1440 px. Сообщи изменённые файлы, результаты проверок и риски.

## 3. Pull Request

После локальной проверки просмотрите diff:

```bash
git diff --check
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
```

Затем создайте один осмысленный commit, отправьте ветку и откройте PR в `main`.
Заполните шаблон: цель, границы, проверки, скриншоты, риски и откат. Не смешивайте
в PR независимые задачи.

GitHub Actions автоматически запускает `npm ci`, `npm run lint` и
`npm run build`. Красный CI — блокер для merge.

## 4. Перекрёстное код-ревью

Если код писал Cursor, откройте PR/diff в Codex и попросите:

> Проведи только код-ревью этой ветки относительно origin/main. Не меняй файлы.
> Ищи регрессии, ошибки данных и localStorage, проблемы hash-маршрутов,
> адаптивности, доступности и безопасности. Сначала перечисли находки по
> критичности с файлами и строками; затем укажи пробелы в проверках.

Если код писал Codex, дайте Cursor тот же запрос в режиме review. Исправления
вносит исполнитель в своей ветке либо отдельный агент в новой ветке — не оба
одновременно.

## 5. Merge и завершение

Merge выполняет человек только после зелёного CI, просмотра diff и закрытия
существенных замечаний. Для одной задачи удобен Squash and merge.

После merge сначала убедитесь, что ветка больше не нужна, и только затем удаляйте
её worktree:

```bash
git worktree list
git worktree remove ../gm-beauty-<agent>-<task>
git branch -d <agent>/<task>
git fetch --prune origin
```

Не используйте `-D`, `--force`, `reset --hard` или `clean -fd` как обычный способ
уборки. Если Git отказывается удалять worktree или ветку, сначала выясните, какие
изменения ещё не сохранены.

## Правило при конфликте

Если обе ветки затронули один файл, не копируйте изменения поверх друг друга.
Сначала завершите и объедините более ранний PR, затем обновите вторую ветку от
нового `origin/main`, разрешите конфликт в её worktree и повторите проверки.
